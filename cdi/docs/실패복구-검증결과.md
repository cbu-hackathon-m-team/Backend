## 다른 담당자 작업과의 분리

- 현재 API 서버 `127.0.0.1:8000`은 중단·재시작하지 않았다. 실행 전후 `/health/live` 모두 200이었다.
- 기존 DB URL·`.env`를 사용하지 않았다. 별도 임시 PostgreSQL 컨테이너와 임의의 localhost 포트를 생성했다.
- 테스트 시작 전에 있던 컨테이너의 ID와 시작 시각이 모두 유지되는 것을 확인했다.
- 이 테스트가 생성한 자식 프로세스만 종료했다. Docker 전체 prune이나 기존 DB 초기화는 하지 않았다.
- 정리 범위는 이 시험이 기록한 UUID 실행 라벨뿐이다.
- 정상·결함·수정 샘플 원본은 수정하지 않았다. 응답 지연은 테스트 어댑터가 생성한 임시 흐름에만 주입했고, 변경된 흐름과 해시를 실행 증거에 보관했다.

## 재실행 방법

Docker가 실행되고 기존 검증 이미지가 준비된 상태에서 프로젝트 폴더에서 한 줄만 실행한다. DB 비밀번호나 환경변수 설정은 필요 없다.

```powershell
.\.venv\Scripts\python.exe scripts/verify_failure_recovery.py
```

실패가 나면 테스트 로그와 증거를 유지하고 해당 시험 자원만 정리한다. 결과 디렉터리는 매번 새 UUID로 생성한다. 실제 강제 종료가 포함돼 있으므로 별도 워커 프로세스와 전용 테스트 DB를 반드시 사용하는 이 스크립트로 실행한다.

## 증거 위치

이번 시험: `artifacts/failure-tests/2586c9a433a14524aa006cf5de13cad5/`

- `summary.json`: 전체 판정, 실행 ID, 잔여 자원 수, 기존 API·컨테이너 상태 확인.
- 각 시나리오의 `evidence.json`: 자원 삭제 후 재조회한 전체 실행 증거.
- `crash/before-recovery.json`: 강제 종료 직후 DB 기록.
- `cleanup/before-recovery.json`: 정리 대기 상태의 실제 기록.
- 각 시나리오의 `.log`: 독립 워커·복구 프로세스 로그.

기본 회귀 테스트도 다시 실행했다: **37 passed, 1 skipped**. 선택 실행 Docker 정상/결함/수정 테스트는 기본 테스트에서 skip되며, 이번 실패·복구 시험은 위 독립 스크립트로 별도 수행했다. Ruff 검사 통과.

## 범위와 다음 역할

이 시험은 실제 실행 워커의 비정상 종료와 새 프로세스의 `Engine.recover()`를 검증한다. 팀이 사용 중인 Uvicorn API 서버를 강제로 끈 시험이나 Windows 재부팅·Docker daemon 전체 장애·실제 디스크 장애 시험은 아니다. 준비 실패와 정리 실패는 재현 가능한 테스트 예외 주입이며 실제 Docker 자체 고장을 일으키지는 않았다.

실행 담당의 다음 일은 API 담당자와 입력·출력 계약을 맞추는 것이다. 프로젝트·테스트 관리 API가 저장된 확정 테스트를 `Snapshot`으로 전달하고, 실행 엔진의 상태·판정·증거·정리 상태를 결과 화면에 연결한다. API 요청·응답 검증 자체는 API 담당자의 작업이다.
