## 후속 실패·복구 검증 완료

실제 Docker 환경의 준비 실패·HTTP 시간 초과·실행 워커 강제 종료 후 새 프로세스 복구·정리 재시도·복구 후 정상 실행을 독립 PostgreSQL에서 확인했다. 5개 시나리오 통과, 모든 시험 실행 자원 정리 완료. 기존 API는 실행 전후 HTTP 200, 기존 컨테이너 시작 시각 유지. 상세 범위와 증거는 [실패복구-검증결과.md](실패복구-검증결과.md)를 참고한다. 기존 API 서버 자체나 Docker daemon 전체를 중단한 시험은 아니다.

## 후속 실제 Docker 검증 — 최신 결과

Docker Desktop 설치 후 실제 PostgreSQL과 Node-RED 4.0.9/4.1.7에서 통합 시험을 실행했다. 아래의 초기 미검증 기록 중 Docker 기동·PostgreSQL 연결·정상/결함/수정 E2E는 이번 결과로 갱신한다. 클라우드 보안·팀 API 통합·실제 프로세스 강제 종료 복구까지 검증했다는 의미는 아니다.

실패 원인: internal 네트워크에만 연결된 컨테이너에서 포트 바인딩 목록이 비어 있었고 기존 코드가 첫 항목을 읽어 IndexError로 중단됐다. Node-RED와 mock은 internal 네트워크에 유지하고, 고정 경로만 중계하는 신뢰된 relay에만 별도 제어 네트워크와 localhost 포트를 부여했다. 이미지 재빌드 완료.

## 자동 테스트에서 확인한 사항

- 미확정 테스트 거절, 중복 실행 슬롯의 원자적 획득, 실행 ID로 상태·결과 조회.
- 가짜 어댑터를 통한 정상·배송 누락·수정 사례의 공통 비교. 두 번째 실제 도구 지원을 의미하지 않는다.
- 기준 환경 위반을 신규 회귀로 오인하지 않음, 단순 차이와 규칙 위반 분리, 미실행 케이스를 미검증 처리.
- 준비 실패, 요청 오류, 작업 시간 초과, 정리 실패, 재시작 중단 처리 및 재시도.
- 실행 완료 저장 후 슬롯 반환 전에 중단돼도 재시작 시 슬롯 복구.
- 과거 실행 입력·기대 기준·결과가 이후 실행으로 변경되지 않음.
- 실제 로컬 HTTP 모의 서버의 재고 차감·배송 요청 기록, 재초기화, 실행 ID 불일치 거절.
- HTTPX 호출 순서(초기화→실행→수집), 원본 노드 ID의 논리 단계 매핑.
- 모의 Docker SDK로 internal 네트워크, loopback 포트, cap_drop, 허용 이미지와 작업별 정리 라벨 확인.
- Docker 생성 호출이 진행 중일 때 취소되더라도 해당 호출이 끝난 뒤 정리하도록 대기.
- 정상/결함 흐름의 차이가 배송 분기 연결 1개뿐이며 수정 흐름은 정상과 같음.

## 아직 확인하지 못한 사항

1. **Docker 실제 실행**: 이 PC에서 Docker CLI·설치 경로를 찾지 못했다. 실제 Node-RED 컨테이너 기동, 두 버전 흐름 호환성, 네트워크 격리, readiness·자원 정리의 실제 Docker 동작은 미검증이다.
2. **실제 PostgreSQL**: ORM 테스트는 임시 SQLite로 실행했다. PostgreSQL 접속, advisory lock, migration 적용은 아직 실행하지 않았다.
3. **전체 시나리오 E2E**: `tests/test_docker_e2e.py`는 위 조건이 없어 기본 실행에서 skip했다. 정상→결함→수정에 대한 기대값을 실제 결과라고 주장하지 않는다.
4. **Playwright 전용 Chromium 설치**: CDN 연결이 반복해서 끊겨 다운로드에 실패했다. 대신 PC에 이미 설치된 Edge에서 Playwright 검증은 통과했다.
5. **팀 API 통합**: 프로젝트·규칙·테스트 관리 백엔드와 실제 연결은 아직 하지 않았다. 확정된 스냅샷을 넘기는 실행 담당용 API와 계약을 제공했다.
