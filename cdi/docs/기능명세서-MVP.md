# 오픈소스 업데이트 영향 검증 서비스 — MVP 기능명세서

> 초기 아이디어 초안입니다. 이후 제공된 `OSSGuard_MVP_구현계획_기능명세서.pdf`를 최신 기준으로 적용합니다. 이 문서의 n8n·Redis·Celery 제안은 현재 구현에 적용하지 않습니다. 현재 담당 범위와 구현 상태는 `docs/실행백엔드-인수인계.md`를 참고하세요.

## 1. 기획 기준

이 문서는 기존 아이디어를 대체하는 이번 아이디어만을 기준으로 한다. 역할은 **백엔드 개발자 총 2명**으로 가정한다. 실제 팀 구성이 다르면 분담을 조정한다.

기업이 수정한 오픈소스를 업데이트하기 전에 기존 업무가 유지되는지 검증하고, 달라진 결과와 관련 코드·로그를 근거로 AI 피드백을 제공한다.

오픈소스가 존재한다는 사실만으로 도입 타당성이 입증되는 것은 아니다. 기능 적합성, 라이선스, 운영 비용은 별도 검토 대상이며, 이 서비스는 그중 **업데이트 시 기존 업무의 회귀 위험을 확인하는 작업**에 집중한다.

### 문제 정의

- 기업은 오픈소스에 맞춤 기능이나 연동 코드를 추가한다.
- 업데이트 후 프로그램이 실행되더라도 일부 업무가 누락될 수 있다.
- 따라서 실행 여부뿐 아니라 주문 접수 → 결제 확인 → 재고 차감 → 배송 요청의 업무 결과를 확인해야 한다.

### 핵심 가치

정상 업무의 입력과 기대 결과를 한 번 등록하고, 업데이트 후보에 같은 시나리오를 실행해 반복 검증한다. 해커톤에서는 자동 시나리오 발견까지 구현하지 않고, 개발자가 구성한 시나리오의 실행 결과를 기록하고 사용자가 기준선으로 승인하는 흐름을 구현한다.

## 2. MVP 범위

| 구분 | 포함 범위 |
|---|---|
| 지원 대상 | n8n 한 종류 |
| 업무 | 주문 처리 시나리오 1개 |
| 입력 | 사전 준비한 기존·후보 이미지, 워크플로 파일, 테스트 입력, 맞춤 코드 diff |
| 실행 | Docker Compose 템플릿으로 기존·후보 환경을 분리 실행 |
| 외부 연동 | 결제·재고·배송 mock 서버 사용 |
| 판정 | 업무 단계, 결과 값, 외부 요청 기록 비교 |
| AI | diff·실행 로그·실패 단계 기반 원인 후보와 수정 방향 제안 |
| 출력 | 검증 상태, 단계별 결과, 근거 로그, AI 분석 보고서 |

제외: 임의 저장소 자동 빌드, 모든 오픈소스 지원, 임의 업무 자동 발견, 운영 환경 연결, 자동 코드 수정·배포, 결제·조직 관리.

시연용 결함은 **맞춤 코드에 의도적으로 넣은 결함**으로 명시한다. n8n 공식 업데이트의 실제 버그라고 소개하지 않는다. 라이선스와 지원 버전은 실제 이미지 선정 시 별도로 확인한다.

## 3. 사용자 흐름

1. 프로젝트를 등록한다.
2. 기존 버전과 업데이트 후보 버전의 사전 준비된 실행 구성을 선택한다.
3. 주문 시나리오와 입력 데이터를 등록한다.
4. 기존 버전을 실행하고 업무 단계·외부 요청·결과를 기록한다.
5. 사용자가 정상 결과를 확인해 기준선으로 승인한다.
6. 업데이트 검증을 요청한다.
7. 워커가 초기 데이터를 같게 맞추고 두 환경에서 동일한 시나리오를 실행한다.
8. 비교기가 차이를 판정하고 AI가 원인 후보를 분석한다.
9. 사용자가 보고서에서 달라진 업무, 근거, 수정 방향을 확인한다.

## 5. 백엔드 2명 역할 분담

### 담당 A — API·데이터·전체 연동

- 프로젝트·버전·시나리오·기준선 CRUD와 검증 요청 API.
- PostgreSQL 스키마와 migration.
- 검증 상태 조회 및 보고서 응답 구성.
- 입력 검증, 멱등성, 공통 오류 응답.
- 저장소 구조, 환경변수 예시, API 문서, 통합 실행 방법.
- 프론트엔드가 있다면 연동 담당. 없으면 API 문서와 간단한 보고서 화면으로 시연.

### 담당 B — 실행 워커·비교기·AI 분석

- n8n 실행 템플릿과 업무 시나리오 fixture.
- 결제·재고·배송 mock 및 요청 기록.
- 동일 초기 데이터 준비, 실행 완료 감지, 타임아웃·정리.
- 결과 정규화와 업무 단계별 비교.
- diff·로그 근거 연결과 LLM 분석 어댑터.
- 정상 후보와 배송 요청 누락 후보를 이용한 통합 검증.

### 함께 먼저 확정할 계약

1. 검증 상태와 판정 값.
2. 작업 메시지 형식: `verification_id`, `schema_version`.
3. 실행 결과와 AI 분석 JSON 스키마.
4. 시나리오의 필수 단계·비교 규칙·기대 외부 요청.
5. 공통 DB 모델. A가 migration을 관리하고 B는 합의된 모델로 실행 결과를 저장한다.

두 명이 파일을 동시에 수정하지 않도록 A는 `api/`, `models/`, `migrations/`, B는 `worker/`, `runner/`, `comparison/`, `analysis/`, `fixtures/`를 주로 담당한다.

## 6. 기초 시스템 구성안

아래 스택은 아직 구현하지 않은 제안이다. 팀에 익숙한 언어가 있다면 역할과 인터페이스를 유지한 채 변경할 수 있다.

| 요소 | 제안 | 목적 |
|---|---|---|
| API | Python + FastAPI | 입력 검증·API 문서·검증 요청 |
| DB | PostgreSQL | 설정·기준선·상태·보고서 저장 |
| 작업 큐 | Redis + Celery | 긴 검증 작업을 API와 분리 |
| 실행 환경 | Docker Compose | 고정된 n8n 테스트 환경 생성 |
| 결과 파일 | 로컬 artifact 디렉터리 | 로그·diff·워크플로 보관 |
| AI 연동 | 교체 가능한 LLM 어댑터 | 구조화된 원인 분석 생성 |

```text
사용자 / 보고서 화면
        │
        ▼
FastAPI ───────── PostgreSQL
        │               ▲
        ▼               │ 결과·상태 저장
Redis → Celery Worker ──┘
           │
           ├─ 기존 환경: n8n + 독립 저장소 + mock
           ├─ 후보 환경: n8n + 독립 저장소 + mock
           ├─ 결과 정규화 → 비교기
           └─ diff + 로그 + 비교 결과 → LLM → 보고서
```

기존과 후보는 DB·볼륨·mock 상태를 공유하지 않는다. 워크플로 실행은 실제 결제나 배송을 호출하지 않는다. MVP는 신뢰할 수 있는 사전 준비 이미지로만 실행하며, Docker 컨테이너를 임의의 비신뢰 코드를 안전하게 실행하는 완전한 보안 경계로 간주하지 않는다.

### 최소 데이터 모델

| 테이블 | 주요 필드 |
|---|---|
| projects | id, name, description |
| versions | id, project_id, role, image_digest, source_revision, workflow_artifact, config_hash |
| scenarios | id, project_id, revision, input_json, expected_steps, comparison_rules |
| baselines | id, scenario_id, version_id, source_run_id, snapshot_json, approved_at |
| verifications | id, baseline_id, candidate_version_id, idempotency_key, status, verdict, analysis_status, error_code, timestamps |

기준선 기록용 run도 별도 실행 상태를 가진다. 승인 후 기준선 스냅샷은 수정하지 않으며, 시나리오 변경 시 새 기준선을 만든다.

### 최소 API

| 메서드 | 경로 | 용도 |
|---|---|---|
| POST / GET | `/projects` | 프로젝트 생성 / 목록 |
| POST | `/projects/{id}/versions` | 실행 버전 등록 |
| POST | `/projects/{id}/scenarios` | 시나리오 등록 |
| POST | `/scenarios/{id}/baseline-runs` | 정상 동작 기록 요청, 202 + run ID |
| GET | `/runs/{id}` | 기록 실행 상태·결과 조회 |
| POST | `/baselines` | 정상 실행 결과 승인 |
| POST | `/verifications` | 검증 작업 요청, 202 + 검증 ID |
| GET | `/verifications/{id}` | 진행 상태 조회 |
| GET | `/verifications/{id}/report` | 보고서 조회 |
| GET | `/health/live`, `/health/ready` | 프로세스·의존성 상태 확인 |

MVP 상태 갱신은 폴링으로 구현한다. 검증 요청에는 `Idempotency-Key`를 사용하며 같은 키에 다른 본문이 오면 409로 거부한다. DB 저장 후 큐 발행이 실패한 작업을 복구할 수 있도록 미발행 작업 재등록 절차를 둔다. 워커는 DB 상태를 원자적으로 선점해 중복 메시지가 중복 실행을 만들지 않도록 한다.

## 7. 판정 및 오류 규칙

작업 상태: `QUEUED → PREPARING → RUNNING → COMPARING → ANALYZING → COMPLETED`. 환경 오류 등으로 검증을 끝낼 수 없으면 `FAILED`로 종료하고 정리한다.

업무 판정과 작업 상태는 분리한다. 업무 회귀를 찾아 정상적으로 보고서를 만든 작업은 `COMPLETED + REGRESSION`이다.

| 판정 | 조건 |
|---|---|
| PASS | 기존 재실행이 승인 기준선과 일치하고, 후보도 모든 필수 검증을 통과 |
| REGRESSION | 기존 재실행은 정상이며 후보에서 필수 단계·외부 요청·업무 결과 차이가 확인됨 |
| INCONCLUSIVE | 기존 재실행도 기준선과 다르거나 환경·관측 실패로 비교 근거가 부족함 |

- HTTP 200이나 n8n 실행 성공만으로 PASS를 내리지 않는다.
- 배송 mock에 주문 ID가 일치하는 요청이 정확히 1회 기록되는지 검증한다.
- 재고는 초기 수량에서 주문 수량만큼 감소했는지 검증한다.
- 시간·실행 ID 등 변동 필드는 명시된 비교 규칙으로만 제외한다.
- 비동기 업무가 끝나기 전에 누락 판정을 내리지 않도록 완료 신호와 관측 제한 시간을 정의한다.
- AI는 판정을 바꾸지 않으며 근거가 없으면 원인을 단정하지 않는다.
- AI 호출 실패는 `analysis_status=FAILED`로 저장하고 비교 보고서는 제공한다.
- 외부 연동 비밀값과 개인정보를 마스킹한 후 AI 입력을 만든다.
- 시작 제한 시간과 실행 제한 시간은 설정값으로 두고, 초과 단계·원인을 보고서에 남긴다.
- 프로세스 중단으로 남은 실행 자원은 검증 ID와 만료 시각을 이용해 회수한다.

## 8. 보고서 구성

1. 검증 대상: 이미지 digest, 코드 revision, 워크플로 revision, 시나리오.
2. 요약: 판정, 실패한 업무, 실행 시간, 분석 상태.
3. 단계 비교: 주문 접수 / 결제 확인 / 재고 차감 / 배송 요청.
4. 관측 근거: 기대 값·실제 값, mock 요청 기록, 실행 로그.
5. 코드 변경: 제공된 diff의 파일과 변경 구간.
6. AI 피드백: 원인 후보, 근거 ID, 수정 방향, 추가 확인 방법.

파일·라인을 제시할 때는 입력 diff나 실제 소스에서 확인된 위치만 사용한다. 관련 코드가 제공되지 않으면 코드 위치는 확인 불가로 표시한다. AI 제안은 적용 전 검토가 필요한 가설로 표시한다.

## 9. 구현 순서 및 완료 기준

| 순서 | 담당 A | 담당 B | 공동 완료 기준 |
|---|---|---|---|
| 1. 기초 실행 | API·DB·큐·migration·환경변수 구성 | 워커 부팅·n8n 정상 시나리오 구성 | 한 명령으로 기본 서비스 기동, 작업 1건 처리 |
| 2. 수직 흐름 | 검증 요청·상태 조회 | 고정 fixture 실행·mock 수집 | API 요청으로 실행 결과가 DB에 저장됨 |
| 3. 회귀 검증 | 기준선 승인·보고서 API | 두 환경 실행·정규화·비교 | 정상 후보 PASS, 배송 누락 후보 REGRESSION |
| 4. AI·시연 | 보고서 연동·오류 응답 정리 | AI 분석·타임아웃·자원 회수 | AI 실패에도 보고서 제공, 종료 후 자원 정리 |

가장 먼저 완성할 것은 **검증 요청 → 워커 → 고정된 n8n 실행 → 배송 요청 확인 → 결과 조회** 흐름이다. 이 흐름을 확인한 뒤 두 버전 비교와 AI 분석을 붙인다.

### 필수 검증 사례

- 정상 기존 버전 + 정상 후보: PASS.
- 정상 기존 버전 + 배송 요청 누락 후보: REGRESSION, 배송 단계와 관측 근거 표시.
- 기존 재실행 실패: 후보 회귀로 오인하지 않고 INCONCLUSIVE.
- 환경 시작 실패·실행 타임아웃: 오류 단계 표시 및 자원 정리.
- AI 응답 실패: 비교 보고서 유지.
- 중복 요청·중복 큐 전달: 검증 중복 생성과 실행 방지.

## 10. 차별화와 사업성 가설

고객은 자체 수정 오픈소스를 운영하는 기업 및 유지보수 SI·MSP 업체다. 기존 테스트 도구 위에 업무 기록·기준선 승인·반복 검증·변경 영향 설명을 묶어 검증 작업을 줄이는 것이 제품의 차별화 가설이다.

해커톤 결과만으로 테스트 작성이 전혀 필요 없다고 주장하지 않는다. 이후 실제 고객 업무에서 최초 시나리오 설정 시간, 업데이트당 검증 시간, 발견한 회귀 수, 오탐·미탐을 측정해 가치와 비용 지불 의사를 확인한다.
