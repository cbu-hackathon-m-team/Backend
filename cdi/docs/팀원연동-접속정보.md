# 실행 엔진 접속·워크플로 전달 정보

확인일: 2026-10-31. 현재 대상은 **Node-RED**이다. n8n은 초기 기획이며 최신 PDF에서는 지원 대상에서 제외됐다. n8n 워크플로 JSON·webhook 주소는 제공하지 않는다.

## 1. 실행 머신

- Windows PC + Docker Desktop Linux engine / WSL2. GCP VM은 사용하지 않는다.
- Wi-Fi IPv4: `10.67.150.24` (현재 사설 주소, 접속 네트워크에 따라 변경 가능).
- WSL 가상 어댑터: `172.24.112.1` (팀원 접속용 주소가 아님).
- 이 PC에서 실행 엔진 API: `http://127.0.0.1:8000`, `/health/live` 응답 200 확인.
- 공개 IP·공개 도메인·외부 접속 경로는 구성하지 않았다.

## 2. 실제 docker ps 결과

```text
NAMES                    IMAGE                PORTS                       STATUS
ossguard-dev-postgres-1   postgres:16-alpine   127.0.0.1:15432->5432/tcp   Up (healthy)
```

현재 결과를 옮긴 텍스트이며 스크린샷이 아니다. 검증 실행 시에만 기준/후보 각각 Node-RED·mock·relay가 생성되고 종료 시 삭제된다. FastAPI는 호스트 Python 프로세스로 실행되므로 docker ps에 나타나지 않는다.

## 3. Backend 저장소에 전달할 파일

- `infra/execution.compose.yaml`: PostgreSQL용 Compose. 범용 `docker-compose.yml` 파일명은 사용하지 않는다.
- `src/ossguard/node_red.py`: 검증 컨테이너는 정적 Compose가 아니라 이 Docker SDK 어댑터가 동적으로 생성·삭제한다.
- `fixtures/node-red/normal.json`, `missing_shipping.json`, `fixed.json`: 정상·배송 누락·수정 Node-RED 흐름.
- `fixtures/node-red/settings.js`, `images.lock.json`, `suite.json`: 런타임 설정·이미지 digest·확정 테스트 샘플.
- `infra/mock.Dockerfile`, `src/ossguard/mock_service.py`, `relay_service.py`: 모의 서비스와 허용 경로 relay.
- 실행·저장·복구 코드, `migrations/`, `tests/`, `scripts/`, 의존성 파일과 문서도 함께 전달한다. Compose와 흐름 JSON만으로는 동적 검증 실행 전체가 구성되지 않는다.
- 실제 `.env`, `.venv/`, 임시 DB와 `artifacts/`는 올리지 않는다. `.env.example`만 공유한다.

현재 로컬 폴더에는 Git 저장소·remote가 없다. 대상 Backend 저장소 URL을 확인한 뒤 별도 브랜치에서 팀 코드와 합쳐야 한다. 현재 업로드는 미실행이다.

## 4. 업무 요청 경로

Node-RED 내부 경로: `POST http://target:1880/orders`.

실행 중 호스트용 경로: `POST http://127.0.0.1:<해당 환경의 relay 포트>/target/orders`.

포트는 기준·후보 환경별로 동적 할당되며 종료 시 사라진다. 고정된 외부 webhook이 아니다. 어댑터 `start()` 후 `Environment.metadata.target_url` 및 `mock_url`에 실제 주소가 들어온다. `<...>`는 설명용 자리표시자이며 그대로 요청하면 안 된다.

아래 초기화 API를 먼저 호출한 뒤 요청한다. 필수 헤더:

```text
Content-Type: application/json
X-Run-Id: demo-run
X-Env-Id: baseline
X-Case-Id: T01
```

본문:

```json
{"paid": true, "stock": 10, "quantity": 2}
```

정상 샘플 T01의 실제 확인 응답 (HTTP 200):

```json
{"accepted": true, "stock": 8}
```

배송 누락 결함 샘플도 HTTP 200일 수 있으므로 배송 이벤트 수를 반드시 따로 검사한다. 현재 모의 서비스의 결제·재고 조건은 reset에서 설정한다. 주문 본문의 stock/paid만 바꿔서는 모의 서비스 상태가 바뀌지 않는다.

## 5. 모의 서비스 초기화·기록 조회

호스트 경로:

- `POST http://127.0.0.1:<relay 포트>/mock/reset`
- `GET http://127.0.0.1:<relay 포트>/mock/state`

컨테이너 네트워크 내부에서는 각각 `http://mock:8080/reset`, `/state`이다.

초기화 본문:

```json
{"run_id":"demo-run","env_id":"baseline","case_id":"T01","stock":10,"paid":true}
```

이후 업무 요청 헤더의 run/env/case ID가 이 값과 같아야 한다. 불일치 시 mock은 409를 반환한다. 초기화는 기존 재고·배송 기록·이벤트를 교체한다. 정상 T01 후 상태 조회 예시:

```json
{
  "run_id":"demo-run", "env_id":"baseline", "case_id":"T01",
  "stock":8, "paid":true, "shipping_count":1,
  "events":[
    {"node_id":"order_receive","event_type":"order_received","payload":{},"sequence":1},
    {"node_id":"payment_check","event_type":"payment_checked","payload":{"paid":true},"sequence":2},
    {"node_id":"inventory_decrement","event_type":"inventory_decremented","payload":{"stock":8,"applied":true},"sequence":3},
    {"node_id":"shipping_request","event_type":"shipping_requested","payload":{"count":1},"sequence":4}
  ]
}
```

위 ID는 설명용이다. 이벤트·수량은 실제 정상 실행에서 확인한 구조다. 결과 DB의 정규화된 이벤트에는 node_id와 함께 step_key가 추가된다.

컨테이너 종료 후에는 mock 조회 주소가 사라지므로 `GET /api/validations/{run_id}`에서 저장된 response/events/logs를 조회한다.

## 6. 다른 PC에서 접속 가능한가?

현재는 불가능하다. PostgreSQL과 relay는 127.0.0.1에만 바인딩하고, API도 localhost 실행 설정이다. 같은 Wi-Fi여도 `10.67.150.24:8000` 등으로 직접 접속할 수 있도록 구성되지 않았다. 다른 PC에서 실제 접속 시험은 하지 않았다.

팀원이 자기 PC에 저장소를 clone해서 실행하면 자기 PC의 localhost에서 사용할 수 있다. 한 머신을 공유하려면 별도 팀 전용 터널 또는 API 바인딩·접근 제어·방화벽 규칙을 합의해 구성해야 한다. DB·Node-RED 관리 화면·Docker 제어 포트를 외부에 공개할 필요는 없다. 이번 작업에서는 기존 서버 바인딩과 방화벽을 변경하지 않았다.

권장 연동 경계는 팀의 API가 실행 엔진에 확정 Snapshot을 넘기고 실행 ID로 증거를 조회하는 방식이다. 임시 Node-RED 포트를 팀원이 매번 직접 호출하도록 구성할 필요는 없다.
