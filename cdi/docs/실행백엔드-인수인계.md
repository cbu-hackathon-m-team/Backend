# OSSGuard 실행 백엔드 인수인계

## 적용 기준과 역할

사용자가 제공한 9쪽 PDF `OSSGuard_MVP_구현계획_기능명세서.pdf`가 최신 기준이다. 초기 n8n 기획을 대체한다. 마지막 범위 정정에 따라 GCP 계정·VM, AI API 계정, 클라우드 배포·운영 준비는 이번 작업에서 제외했다.

담당 범위는 Docker 환경 제어, HTTP 실행·수집, 실행 결과 이력이다. PDF P0의 F06·F07·F08·F12·F13을 중심으로 구현했고, 독립 검증을 위해 F05의 실행 시작·조회와 F09의 비교 코어를 포함했다. Playwright는 기존 담당 범위의 보조 모듈로 유지한다. 핵심 업무 판정은 브라우저 화면이나 HTTP 200이 아니라 실제 모의 API 기록을 근거로 한다.

다른 백엔드 담당 영역: 프로젝트·규칙·테스트 관리(F01~F04), AI 테스트 생성 및 원인 분석(F03·F11). 프론트엔드 결과 화면(F10)은 구현하지 않았다. 계정·로그인·다중 워크스페이스도 범위에 포함하지 않는다.

## 실행 계약

`POST /api/validations`는 현재 **확정된 Snapshot 전체**를 받는 실행 담당용 연동 API다. 입력 예시는 `fixtures/node-red/suite.json`이다. 프로젝트/테스트 ID를 받아 DB에서 내용을 읽는 전체 플랫폼 API는 아직 아니다.

팀 통합 시 다른 백엔드가 확정 테스트와 프로젝트 설정을 조회한 뒤 `Snapshot`으로 변환해 `Engine.submit(snapshot)`을 호출한다. 사용자 요청의 `confirmed=true`만 신뢰해 확정을 대신하면 안 된다. 프론트엔드에 바로 노출할 때에는 다른 백엔드의 확정 여부 조회와 접근 제어가 필요하다.

`GET /api/validations/{UUID}` 응답:

- `status`: QUEUED / PREPARING / RUNNING_BASELINE / RUNNING_CANDIDATE / COMPARING / CLEANING / COMPLETED / FAILED / INTERRUPTED.
- `snapshot`: 실행 당시 규칙, 테스트, 입력, 기대 조건, 단계 매핑, 버전·샘플 선택.
- `results`: 환경·케이스별 response/events/logs/step_map/artifact_refs, COMPLETE/ERROR/UNVERIFIED.
- `report.comparisons`: 케이스별 판정, 각 비교식의 기대값·실제값, 전후 차이 여부.
- `report.environments`: 이미지 ID·digest, 어댑터 버전, 흐름 JSON·해시, 실행 설정.
- `report.artifact_diff`: 기존·후보 업무 흐름의 실제 변경 내용.
- `report.analysis_status`: 현재 NOT_CONFIGURED. AI 완료를 가장하지 않는다.
- `report.cleanup_status`: COMPLETE / PENDING. 판정과 별도로 제공한다.

판정은 PASS / REGRESSION_SUSPECTED / BASELINE_REVIEW / EXECUTION_ERROR / UNVERIFIED다. 기대 조건을 만족하면서 값만 다른 경우 PASS와 `different=true`가 함께 나올 수 있다. 기준 환경도 위반하면 신규 회귀로 단정하지 않는다.

현재 artifact_refs는 빈 배열이며 로그·흐름·diff는 DB JSON 안에 보관한다. 별도 파일 저장소를 도입하면 artifact_refs에 연결할 수 있다. 저장소 모델은 `validations`, `test_results`, `execution_slot` 세 테이블을 제공한다. 팀 통합 migration과 합칠 때 테이블명과 revision을 조율해야 한다.

## 샘플과 버전

- Node-RED 4.0.9와 4.1.7의 공개 이미지 존재를 확인하고 `images.lock.json`에 digest를 기록했다. Docker SDK는 태그 대신 이 digest를 조회하고 실제 이미지 ID로 컨테이너를 만든다.
- `normal.json`: 주문→결제→재고→배송.
- `missing_shipping.json`: 재고 처리 성공 이후 배송 분기 대신 종료 노드로 연결하는 의도적 결함.
- `fixed.json`: 배송 연결을 복구한 정상 흐름. 정상 파일과 같은 내용이다.
- `suite.json`: PDF T01~T04의 입력과 기대 결과. 문서에 명시된 값을 기본 확정 테스트로 구성했다.
- `settings.js`: Node-RED 관리 화면·편집기 비활성화. 외부 모듈 설치 금지.

정상 대조군과 수정 후보는 모두 통과해야 하며, 결함 후보는 T01·T02에서 배송 누락으로 위반해야 한다. 이는 기대값이며 Docker 실제 실행 결과가 나오기 전까지 공식 업데이트 호환성이나 실제 회귀 탐지 완료로 소개하면 안 된다.

## 자원과 오류 처리

검증 컨테이너에는 AI 키·DB 비밀번호·호스트 Docker 소켓을 전달하지 않는다. Node-RED와 mock은 환경별 internal 네트워크에만 연결한다. 신뢰된 relay가 별도 제어 네트워크와 internal 네트워크에 연결되어 허용된 health/reset/state/orders 경로만 중계하며, relay의 호스트 포트만 loopback에 바인딩한다. 임의 목적지와 관리 화면은 중계하지 않는다. 검증 자원에는 owner/run/env 라벨을 달고 해당 실행의 라벨에 일치하는 컨테이너·볼륨·네트워크만 정리한다. 플랫폼 PostgreSQL 볼륨은 이 정리 대상이 아니다.

요청 시간 초과·증거 수집 오류가 난 환경은 다음 케이스를 실행하지 않는다. 늦게 끝난 요청이 다음 케이스 초기값을 오염시키지 않도록 하기 위해서다. 실행하지 않은 케이스는 UNVERIFIED로 저장한다.

DB에 증거를 보관하기 전에 DB 장애가 발생하면 자원을 파괴하지 않고 작업을 남긴다. 서비스 복구 후 실행 상태를 INTERRUPTED로 바꾸고 로그를 수집한 뒤 라벨 기반 정리를 재시도한다. 정리 실패가 남으면 다음 실행을 막는다.

PostgreSQL advisory lock으로 실행 워커를 1개로 제한한다. Uvicorn은 `--workers 1`로 사용한다. 개발용 SQLite는 계약·회귀 테스트 전용이며 다중 프로세스 지원을 주장하지 않는다. `/health/ready`는 DB 접속만 확인하고 Docker 준비 여부는 검증 실행 시 확인한다.

이 격리는 팀이 준비한 허용 샘플을 실행하기 위한 것이다. 외부 사용자의 임의 코드 실행이나 클라우드 메타데이터·호스트 전체에 대한 보안 검증까지 완료한 것은 아니다.

## 검증 상태

실행 결과는 `docs/검증기록.md`에 별도로 기록한다. 실제 Docker와 PostgreSQL 통합 시험은 설치된 Docker daemon이 필요한 선택 실행 테스트로 제공한다. 테스트 더블로 통과한 항목과 실제 런타임에서 확인한 항목을 구분한다.
